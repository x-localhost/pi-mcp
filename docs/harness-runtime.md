# Runtime acceptance, review, sessions, and observation

`pi_capabilities` returns versioned safe IDs and descriptions for the configured model, verifier commands, offline materials, and tools available in each mode. It also lists continuation operations and bounded context/observation settings. It does not return verifier argv, material manifest paths, MCP environment values, or credentials.

An optional version-1 acceptance contract has `required_verification_ids`, `required_artifact_paths`, and `require_review`. Required paths are exact normalized relative source paths. They may refer to unchanged regular files in the committed base, unchanged pinned materials, or regular files in the immutable code checkpoint. Reports and deletions never satisfy a source path. Followups and forks inherit the contract and verifier selection; a child can add requirements but cannot remove inherited ones. Every child computes its own acceptance from its final code and verifier results. No contract reports `not_requested`.

`execution`, `verification`, and `acceptance` are separate status objects. `acceptance.status` can be `execution_incomplete`, `verification_incomplete`, `missing_artifacts`, `pending_review`, `review_rejected`, or `accepted`. The acceptance evidence reports source job ID, the immutable code `inputSnapshotDigest`, canonical `contractDigest`, and current artifact `manifestSha256`. Report attachment can change the manifest digest without changing code or invalidating a review attestation. An attestation binds the stable source job, code digest, and contract digest.

`pi_review` starts a separate worktree from the terminal source's immutable **code** checkpoint. It restores source changes, starts a fresh Pi session, and exposes only read tools and administrator-declared review tools. It does not copy the author's raw session or conversation. A review job records source job ID, source code digest, and source contract digest. Its final code checkpoint must still match the source before attestation. Review prose is advisory. `pi_attest_review` records an explicit `approved` or `rejected` verdict with **caller authority**; the service does not authenticate a human reviewer or trusted grader. The latest matching verdict controls acceptance, and a rejection revokes an earlier approval.

`pi_rollover` restores terminal code into a new worktree and fresh session with a bounded structured handoff: original objective, original/current constraints, latest request, observed verification/acceptance, pending work, and lineage. It refuses oversized mandatory fields instead of silently truncating them. Old raw history remains private in its original session directory. The rollover writes a durable session seal; later implicit resume through any alias of that session is refused, including after the rollover child is cleaned. An explicit rollover may select older immutable code. Ordinary `pi_followup` automatically rolls over when raw history approaches 16 MiB or has exceeded that checkpoint limit, but only from the latest worktree tip whose current code matches the terminal checkpoint. A raw session exceeding 16 MiB makes raw resume unavailable; completed code, verification, artifacts, and code-only review remain valid.

Rollover jobs expose `rolloverFromId` and `rolloverSourceSnapshotDigest` so a parent workflow can reconcile a submitted child after a restart. The digest is the source's final `artifacts.inputSnapshotDigest`; the child's final code digest is computed separately.

Administrator verifier commands remain separate from protected graders. A command without `protectedFiles` is reported as `repository_controlled_command`, even when its interpreter is image-packaged. A protected declaration pins bounded root-owned regular script and asset files under `/opt/project-tools` by SHA-256, and a declared script or executable must appear in argv. The runtime checks ownership, symlinks, file type, length, hash, and file identity before and after execution. A failed preflight or changed file fails verification. This is an integrity contract for declared packaged files, not per-user OS isolation or a claim that arbitrary repository tests are trusted external graders.

Observation writes bounded metadata-only records to private per-job files: tool timing/error, provider attempt/retry, compaction, context reduction, and activity. Public events contain only allowlisted metadata and generated opaque IDs. `heartbeatAt` means the worker is alive; `lastProgressAt` means useful work was observed. Optional idle and repeated-tool-failure thresholds default to disabled (`0`). A policy stop reports `idle_timeout`, `tool_failure_limit`, or `context_limit`, and the worker still attempts to checkpoint code. Trace headers are injected only when the fixed internal profile has been validated, the selected provider/model matches its fixed loopback endpoint, and the queued dispatcher carries that validated marker. The gateway consumes these private headers rather than forwarding them upstream.
