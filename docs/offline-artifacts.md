# Offline materials and job artifacts

The agent keeps its network disabled. Administrators prepare project dependencies and large data ahead of time. A job selects declared material IDs; it cannot choose source paths, run an install hook, or fetch missing data. Project compilers and package managers belong in a reviewed image. The example [project Dockerfile](../internal-agent/Dockerfile.project.example) pins Node 24.22.0 by digest and uses an administrator-supplied npm cache with `npm ci --offline --ignore-scripts`. Build that image on the designated remote host, review it, and pin the resulting image digest for both internal services. This recipe does not alter the runtime profile or mount policy.

`scripts/pack-material.mjs <source-directory> <40-char-source-commit> [original-LFS-pointer-tree]` emits a version 1 JSON bundle to stdout. The packer reads regular files only and refuses links, devices, Git administration, ambiguous paths, and more than 1,024 files, 8 MiB per file, or 64 MiB total decoded content. The optional original tree adds an expected original SHA-256 for every LFS overlay file. The source commit must be the exact commit selected for the job; a submodule bundle uses the parent repository commit and targets a declared gitlink. The bundle has one SHA-256 per blob and is itself pinned by SHA-256. Preparing its contents and license review are administrator responsibilities.

For an isolated agent, send the bundle through stdin to `node /app/internal-agent/import-material.mjs <id> <bundle-sha256> <source-commit>`. The import validates all entries and writes a new private `/var/lib/pi-mcp/materials/<id>.json`; it refuses existing IDs. It never extracts an archive or mounts the host source tree. A declaration in administrator configuration uses `offlineMaterials.materials` entries of this form:

```json
{
  "id": "dependency-cache",
  "manifestPath": "/var/lib/pi-mcp/materials/dependency-cache.json",
  "manifestSha256": "<64 lowercase hex characters>",
  "baseCommit": "<40 lowercase hex characters>",
  "destination": "vendor",
  "collision": "reject"
}
```

`collision` is `reject`, `overlay-lfs`, or `submodule`. An LFS overlay requires each manifest entry's expected original hash and a tracked regular file at the destination. A submodule overlay additionally requires `submoduleCommit` with the exact 40-character gitlink commit at the pinned parent commit, plus an empty target directory. All selected materials are validated before any worktree write; wrong commits, hashes, path aliases, unsafe files, or collisions reject the selection. The runtime stores `inputMaterialsDigest` and `materialBaseline` returned by `applyOfflineMaterials`; it passes both to `snapshotArtifacts`. Unchanged imported files then remain input baseline, while model edits to those files appear as changes. A fork reapplies the same pinned materials to a fresh base worktree before `restoreCheckpoint` verifies the baseline and restores model changes.

After all model and verifier writers have stopped, `snapshotArtifacts` captures a private raw checkpoint and a separate public manifest and blobs. The private checkpoint retains exact changed/new regular-file bytes, modes and deletions; renames are a delete and a new file. It is accessible only to the manager's fork path. The public export contains sanitized text or exact binary bytes when a scan finds no known secret. Binary with a detected secret is omitted, with an explicit reason. Binary hunks in a generated patch (see below) only ever come from public bytes that already passed this scan, and the patch generator scans the base side of each change again before using it; the applicable meaning stated there is "complete, unredacted patch of supported exported source changes relative to baseCommit; not proof of target compatibility, verification, acceptance or review". Redacted or omitted output sets `exportComplete: false` and `applicable: false`; a private checkpoint can still be complete. Hashes on public entries describe exported bytes. No claim is made that secret scanning finds every possible secret.

`pi_patch` turns a terminal job's exported `file`/`delete` manifest entries (report entries are never part of it, by type, not by path, so a real source file at `reports/x` is still included) into one sanitized unified diff against the job's literal `baseCommit` tree, bound and cached under `<job>/patch/`. The base side of every change is resolved by walking literal tree metadata at `baseCommit`; a symlink or gitlink anywhere on the path, any mode other than a regular file, an oversized base blob, or a secret found in a base binary all make that change unsupported and leave the whole patch `applicable: false`, with the specific reasons listed in `notApplicableReasons`. An entry whose public path was itself redacted is never used to look up the base file. The final patch text is sanitized once more before anything is cached or returned; only the sanitized bytes are ever written or returned. `pi_patch` pages its result like `pi_read_artifact`, with `include_text: false` for a metadata-only preview first. Apply a downloaded patch with `git apply --check` and then `git apply` in a clean integration worktree checked out at `baseCommit`; `--3way` is available as an explicit option for a target that has since diverged, but it touches the index and can leave conflict markers. Unchanged imported materials are not part of the patch, the same as they are not part of the artifact export.

The optional report allowlist captures `result.json`, `verification.json`, `stdout.log`, and `stderr.log` from the job directory under the logical names `result`, `verification`, `stdout`, and `stderr`. Reports are sanitized public output only and never enter the raw fork checkpoint. The runtime selects existing reports explicitly when it snapshots. Readers use `listArtifacts` with entry and omission cursors and `readArtifact` with offset/length; each read is bounded and returns a page hash, full blob hash, next offset and EOF. Exports larger than an inline response remain available through successive pages.

`node /app/internal-agent/export-artifacts.mjs <job-id>` runs under the shared manager lock and emits only the verified public manifest bundle to stdout for a terminal job. Pipe it to `node scripts/save-artifact-export.mjs <new-output-file>` on the host. The saver verifies the manifest and every included blob before creating a new mode-0600 file; it never extracts paths or overwrites a file. Keep the exported bundle private if it contains project data. `manifestSha256`, entry hashes, `checkpointComplete`, `exportComplete`, `truncated`, `omittedCount`, and `inputSnapshotDigest` give the caller evidence about completeness and identity. These digests are integrity checks for the stored bytes, not signatures against a state-volume attacker.

`node /app/internal-agent/export-patch.mjs <job-id>` builds the cached patch for a terminal job if needed, then writes exactly those cached bytes to stdout and `{ sha256, totalBytes, applicable }` to stderr; it never sets `exportedAt`. Run `docker compose … exec -T agent node /app/internal-agent/export-patch.mjs <id> > job.patch` on the host and verify the printed sha256 against the saved file before relying on it.

Default artifact limits are 256 changed files, 2 MiB per file, 32 MiB total raw content, and 64 KiB per read page. Administrators may raise them to 4,096 files, 16 MiB per file, 128 MiB total, and 256 KiB per page. An exceeded limit is explicit and makes the checkpoint or export incomplete; a fork must reject an incomplete checkpoint. The runtime should count private checkpoint, public blobs, imported materials, and staging in its disk admission policy. The image recipe supplies toolchains; imported material remains data and does not authorize runtime installs, hooks, general network access, or new trusted MCP executables.
