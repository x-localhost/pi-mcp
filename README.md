# Pi MCP

[사내 전용 격리 Pi 에이전트 설정](docs/internal-agent.md)은 별도 opt-in Docker 프로필입니다.

Pi MCP delegates bounded coding and review tasks to [Pi coding agent](https://github.com/earendil-works/pi) through a stdio MCP service. Each new task starts at a committed Git ref in its own branch and worktree. It returns a job ID immediately; queued and running work continues if the MCP client disconnects. Normal followups reuse the current unsealed session; long sessions can continue from preserved code in a fresh session. The completion APIs add events, interactive controls, verification, artifacts, forking, recovery and cleanup; see the [runtime guide](docs/completion-runtime.md) and [harness guide](docs/harness-runtime.md).

## Install and configure

Use Node.js 22.19 or newer on a Linux runtime with `/usr/bin/flock` and visible `/proc` process identities. Isolated Docker is preferred when the MCP client runs on a Mac. Run `npm ci` in this repository. The lockfile pins Pi 1.4.0; the service rejects a different Pi version. Install `rg` and `fd` on the worker host for Pi's grep/find tools. `pi_health` reports whether they are on the child PATH without making a provider request. Stop all workers using the prior lock implementation before upgrading; do not mix old and new workers in a rolling upgrade.

Create a private JSON configuration from [examples/config.example.json](examples/config.example.json). Set absolute `piPath`, `stateDir`, and `allowedRoots`; set `piArgs` if `piPath` launches Node rather than the Pi executable. Configure both `provider` and `model`, or supply a pair in `pi_delegate`. A model-only override uses the configured provider; a provider override requires a model. Keep the config and state directory owner-private. Point your MCP client at `node /absolute/path/to/pi-mcp/src/server.mjs` with `PI_MCP_CONFIG=/absolute/path/to/config.json`; [examples/mcp.example.json](examples/mcp.example.json) shows the client shape. [Corporate setup](docs/corporate-setup.md) covers proxies, CA certificates, private registries, local cloned repositories, and custom LLM gateway `headers` (see [examples/models.example.json](examples/models.example.json)); missing or invalid header configuration is rejected before any provider request.

`pi_health` checks executable version, configured paths, credential presence, concurrency and tool prerequisites. Credential presence does not prove provider authentication. The service does not make a paid model call for health.

## Task lifecycle

Call `pi_delegate` with an absolute repository root, title, prompt, and optional committed `base_ref`. The selected commit is checked out in `stateDir/worktrees/task-…` on a `codex/pi/…` branch. Dirty source changes, ignored files, and `.env` are not copied; the response warns when the source is dirty. Send context in the prompt and review the preserved worktree before integration. `request_id` makes an exact retry idempotent and rejects a conflicting retry.

Use `pi_status` (optional wait up to 45 seconds), `pi_result`, and `pi_list` to observe queued and running work. The worker marks execution success only after Pi emits `agent_settled`, a final assistant response, and a clean stop reason. Verification has its own status. Failed, cancelled, timed-out and interrupted worktrees remain intact. `pi_cancel` requests queue clearing and abort, then terminates the Pi process group. Uncertain process ownership quarantines the job; recovery is available only after process identity can be proved. `pi_followup` normally starts a new job record using the latest parent worktree and saved session; near the raw-history bound it creates a fresh code-preserving continuation. A recorded but missing session fails closed; the parent result remains available.

`pi_capabilities` lists configured options without exposing private paths or credentials. Versioned acceptance contracts carry required verification, artifacts and review across continuations. `pi_review` uses an immutable code snapshot and a separate read-only session; `pi_attest_review` records an explicit caller verdict bound to that snapshot. `pi_rollover` preserves code and bounded authoritative instructions while sealing old history. See the [harness guide](docs/harness-runtime.md) for limits and trust semantics, and the [workflow guide](docs/harness-workflow.md) for durable sequential stages, observed usage budgets and restart recovery.

Results contain bounded sanitized text, progress, usage, permission denials and a diff preview. Completed work also has paged, bounded artifact snapshots for eligible changed and new files, with digests and explicit omissions; see [offline materials and artifacts](docs/offline-artifacts.md). Full raw Pi session history stays in the private `stateDir/sessions` tree and may contain prompts or provider data. Do not share it as a public artifact. The service never commits, merges, pushes, clones, or publishes on behalf of a task.

## Permissions and trust

Pi starts with ambient extensions, MCP servers, skills, prompt templates, themes, project context files and project approval disabled. It explicitly loads a policy extension and waits for its readiness acknowledgement before any prompt. Review mode exposes read, grep, find and ls. Implement mode also exposes write, edit and `safe_shell`. Administrators may explicitly enable pinned MCP tools, with a separate review allowlist; see [approved MCP](docs/approved-mcp.md). Paths are checked against the canonical worktree and Git administration paths are protected. Built-in bash is disabled. `safe_shell` accepts only an administrator-configured **exact full command**, such as `npm test`; it does not do prefix matching. An approved command can run repository scripts with the worker's OS permissions. This policy controls Pi tools; it is not an OS sandbox. Use trusted repositories and commands.

The runtime seeds only explicit `models.json` and `auth.json` into its private shared agent directory. Shared auth lets Pi coordinate OAuth refresh across workers. Existing refreshed auth is never overwritten by the original seed. A copied login from another Pi agent directory may still be invalidated remotely by a competing refresh; a dedicated pi-mcp login is safest. Command-based credential values in models/auth are rejected. Changing the model file requires stopping jobs and an explicit agent configuration reset. Pi runs offline for startup/catalog traffic but still sends model requests to the selected provider. `HTTP_PROXY` and `HTTPS_PROXY` control Pi's HTTP dispatch; `ALL_PROXY` is forwarded for Git/tooling but alone is not a Pi HTTP proxy setting.

Run the full suite on an appropriate Linux build host. Approved-MCP tests require the root-owned packaged fixture under `/app/approved-mcp`; use the disposable Docker setup and exact full-suite command in the [runtime test report](docs/completion-runtime-report.md). This fixture is for tests only and does not belong in a production image. The suite includes fake Pi process lifecycle tests, actual MCP stdio, and released Pi 1.4.0 against a local mock model gateway. No paid provider keys are needed for those tests.

The [operations guide](docs/operations.md) covers day-to-day use. Actual corporate endpoint acceptance and per-user OS isolation remain separate validation work; local mock tests do not establish either.
